# Conversation Logging (шифрованный лог запрос/ответ LLM)

## Scope Snapshot

- In scope: фиксировать исходный запрос пользователя (messages), доказательство применённого mask (что именно заменено плейсхолдерами) и итоговый ответ LLM для proxy-запросов — как non-streaming (JSON-тело), так и streaming (SSE-лента verbatim); хранить зашифрованными в PostgreSQL; отдавать в admin UI (новая страница Conversations) с расшифрованным содержимым в base64. Запись в БД — асинхронная (фоновые goroutines), не влияет на latency ответа.
- Out of scope: key rotation/KMS, редактирование/экспорт разговоров, per-tenant включение.

## Цель

Администраторы получают возможность в UI видеть, что именно пользователь отправил в LLM, что вернулось — и **как был применён mask**: какие значения детектора (PII/словарь) и какими плейсхолдерами заменены. Сейчас содержимое диалога нигде не персистится, а usage-счётчики хранят только токены/стоимость. Успех фичи: лог разговора с mask-доказательством, зашифрованный в БД, отображаемый в admin UI; ключ шифрования — через ENV; от фронта содержимое приходит в base64-обёртке; запись выполняется асинхронно и не тормозит прокси.

## Основной сценарий

1. Стартовая точка: клиент отправляет POST `/api/v1/chat/completions` (или `/api/v1/messages`) с валидным tenant API-ключом — non-streaming (`stream: false`) или streaming (`stream: true`).
2. Основное действие: gateway перехватывает тело запроса (до mask-преобразования shield), собирает от shield mapping «плейсхолдер → оригинал» (что замаскировано) и итоговое тело ответа (после unmask; для streaming — полная SSE-лента verbatim, как отдана клиенту); кладёт «сырые» данные в буфер фоновых goroutines. Фоновый worker шифрует их (AEAD, ключ из ENV) и батчами пишет в PostgreSQL — на горячем пути нет ни крипты, ни БД.
3. Результат: администратор открывает страницу Conversations в admin UI, видит список (tenant, model, время, статус, флаг masked, флаг streamed), открывает детали — содержимое приходит с API расшифрованным и обёрнутым в base64; фронт декодирует и показывает запрос, как применён mask (оригинал → плейсхолдер) и ответ (для streaming — raw SSE-лента как транскрипт).
4. Ошибка: если фича включена, но ключ ENV не задан — gateway не стартует (fail-closed). Если шифрование/запись падает во время запроса — запись роняется с warn-логом, но прокси продолжает работать (не ломаем data plane).

## User Stories

- P1: администратор видит в UI список разговоров, содержимое запроса/ответа и применение mask (какие значения были заменены плейсхолдерами) для конкретного запроса.
- P2: записи старше TTL автоматически удаляются; запись не влияет на latency ответа (асинхронно).

## MVP Slice

- Захват (оригинал + mask-доказательство + ответ) для non-streaming и streaming запросов; асинхронная запись в БД фоновыми goroutines; read-API (list + detail) с base64-обёрткой; страница Conversations в UI; fail-closed при отсутствии ключа; устойчивость data plane к сбоям конвейера.
- Закрывает первым: AC-001, AC-003, AC-004, AC-005, AC-006, AC-008, AC-010, AC-011.

## First Deployable Outcome

- `curl` запроса на gateway (non-streaming и `stream:true`) → в Postgres появилась зашифрованная запись (просмотр через psql: ciphertext, не plaintext; у stream-записи `streamed=true`, `response` — ciphertext SSE-ленты).
- `curl -H "Authorization: Bearer <admin>" /api/v1/conversations` → список; `/api/v1/conversations/:id` → `payload.request`/`payload.response` как base64.
- Вручную видимая страница `/conversations`, где `atob` раскрывает исходный запрос и ответ (для stream-записей — raw SSE-транскрипт).

## Scope

- Новый middleware (или writer) в цепочке proxy-роутов gateway для захвата тела запроса и ответа `/chat/completions` и `/messages` — non-streaming (JSON) и streaming (SSE-лента verbatim), плюс сбор mask-доказательства из shield.
- Небольшая интеграция в shield-мидлвару: экспонировать построенный mapping «плейсхолдер → оригинал» (dict + PII) через gin context для захвата conversation-логгером.
- Новый Postgres-репозиторий записей разговора + миграция (новая таблица `conversation_logs`).
- Фоновые goroutines: worker (шифрование + batch-запись) и cleanup worker (TTL) — паттерн Analytics; на горячем пути только буферизация + enqueue.
- Крипто-пакет: AEAD (AES-256-GCM), ключ из ENV.
- Admin handler (list/detail), DTO, роуты `/api/v1/conversations`, защищённые admin-сессией.
- Cleanup worker с TTL (по образцу cleanup_worker для usage_raw).
- Новая UI-страница Conversations + пункт меню + роут в `App.tsx`.
- Swagger OpenAPI: секция conversations.

## Контекст

- Proxy-цепочка `server.go` (`RegisterProxyRoute`): chain = WrapSSE → session → shield → usage → handler. Тело запроса читается в shield-мидлваре (оригинал), затем `c.Request.Body` заменяется замаскированной версией. Для фиксации «исходного сообщения» захват должен происходить до shield.
- Ответ: usage-мидлвара уже перехватывает тело ответа non-streaming через кастомный `usageBodyWriter`; аналогичный паттерн применим для финального ответа (то, что получил клиент, т.е. после unmask).
- Mask-доказательство: shield-мидлвара строит `dictMaskMapping` (merged dict+PII) локально в closure. Для того чтобы conversation-логгер (который стоит ДО shield) получил mapping, shield минимально расширяется: после построения mapping кладёт его копию в gin context (`c.Set(conversationMaskKey, ...)`); логгер читает его после `c.Next()` (RQ-007).
- Валидация гида по конфигу: только через viper + `CONFIG_*` ENV; ключ шифрования должен читаться отдельным ENV-переменным напрямую (не через config.yaml), чтобы не попадать в файлы конфигурации.
- Данные пишет gateway-бинарник, читает/расшифровывает admin-бинарник — общий PostgreSQL, ключ в ENV у обоих.
- Incidents (прежнее место для контента) убраны — теперь контент живёт только в этой фиче.

## Зависимости

- Внутренние: существующий пул PostgreSQL, admin-сессия (`adminSessionMw`), конфиг-инфраструктура, паттерн `cleanup_worker`/`AsyncWorker`.
- Внешние: `none` (шифрование реализуется стандартной криптографией Go; конкретный механизм — в plan).
- Меж-спековые: `none` (не зависит от активных специй).

## Требования

- RQ-001: система ДОЛЖНА фиксировать запрос/ответ для `/api/v1/chat/completions` и `/api/v1/messages` при включённой фиче — как для non-streaming (JSON-тело ответа), так и для streaming (`stream: true`, SSE-лента ответа verbatim).
- RQ-002: сохранённые запрос/ответ ДОЛЖНЫ храниться в зашифрованном виде (AEAD), а не plaintext.
- RQ-003: ключ шифрования ДОЛЖЕН задаваться через ENV; при включённой фиче без ключа gateway ДОЛЖЕН завершить старт с ошибкой.
- RQ-004: admin API ДОЛЖЕН отдавать расшифрованное содержимое, обёрнутое в base64 в поле `payload`; в метаданных (list) содержимого быть не должно.
- RQ-005: система ДОЛЖНА удалять записи старше TTL через фоновый cleanup.
- RQ-006: поток прокси не должен ломаться при ошибках захвата/шифрования/записи лога.
- RQ-007: система ДОЛЖНА сохранять доказательство применённого mask — mapping «плейсхолдер → оригинал» (dict + PII — merged) для записей, где mask применялся.
- RQ-008: шифрование и запись в БД ДОЛЖНЫ выполняться асинхронно в фоновых goroutines; обработка ответа клиенту не должна ждать завершения записи.
- RQ-009: для streaming-запросов запись ДОЛЖНА помечаться флагом `streamed`; ответ хранится как verbatim SSE-лента, обрезанная до лимита контента (1 МБ).

## Вне scope

- Агрегация/парсинг SSE-чанков в «чистый» текстовый ответ на стороне gateway — хранится verbatim-лента, показ в UI — транскрипт raw SSE; при необходимости читаемая реконструкция остаётся кандидатом на отдельную фазу.
- `/completions` (legacy text completion) — там свой стаб-хендлер.
- Key rotation / KMS / внешние секрет-менеджеры.
- Редактирование, удаление вручную, экспорт разговоров, аудит чтения разговоров.
- Per-tenant включение/выключение фичи.
- Дополнительное obfuscation содержимого на транспортном уровне сверх base64; base64 — не граница безопасности, только формат передачи.

## Критерии приемки

### AC-001 Захват запроса и ответа (non-streaming)

- Почему это важно: основа фичи — без записи диалога нет смысла в UI.
- **Given** включённая фича и valid tenant API key; non-streaming POST `/api/v1/chat/completions` с `messages` (в т.ч. user message) и `stream: false`; shield возвращает clean; провайдер отвечает 200.
- **When** запрос завершается успешно.
- **Then** в БД появляется запись `conversation_logs` с `tenant_id`, `model`, `created_at`, булевым `masked`, зашифрованными `request` (исходные messages без плейсхолдеров mask), `masking` (mapping «плейсхолдер → оригинал», если mask применялся; иначе null) и `response` (тело, которое увидел клиент, после unmask).
- Evidence: после обращения `psql`/SQL-select возвращает строку; расшифровка ключом ENV даёт исходный prompt, mapping mask и полный итоговый ответ; `response` совпадает с телом, полученным клиентом. Примечание (пост-verify T6.1): запись создаётся только для запросов, где маска применена, ИЛИ запрос заблокирован; чистые незамаскированные запросы не логируются (`masking`=null/`masked`=false-записи отсутствуют).

### AC-002 Захват заблокированных запросов

- Почему это важно: блокировки shield — самый важный случай для аудита.
- **Given** включённая фича; запрос, который shield блокирует (403, `X-Shield-Status: blocked`).
- **When** запрос отклоняется shield.
- **Then** запись создаётся с исходным `request`, пустым/`null` `response` и `status=blocked`.
- Evidence: новая строка в `conversation_logs` со статусом `blocked`; расшифрованный `request` содержит исходный prompt.

### AC-003 Стриминг фиксируется (SSE verbatim)

- Почему это важно: стриминг — большая доля реального трафика; без него инциденты на stream остаются невидимыми в admin.
- **Given** включённая фича; `stream: true` POST `/api/v1/chat/completions`; shield возвращает clean; провайдер шлёт SSE-чанки и терминатор `[DONE]`.
- **When** поток завершается (клиент получил `[DONE]` или соединение прервано).
- **Then** создаётся запись `conversation_logs` с `streamed=true`, исходным `request`, mask-доказательством (если применялся) и `response` = verbatim SSE-лента (то, что увидел клиент, после unmask), обрезанная до 1 МБ; поток, завершившийся `[DONE]` — `status=ok`, без `[DONE]` (обрыв/ошибка) — `status=error`.
- Evidence: middleware-тест stream → в буфере store появляется запись со `streamed=true` и непустым `response`; raw SSE-лента в `response` совпадает с тем, что клиент получил.

### AC-004 Хранение в зашифрованном виде и корректный ключ

- Почему это важно: безопасность at-rest — контент не должен читаться из БД.
- **Given** существующая запись в `conversation_logs`.
- **When** запись просматривается напрямую в БД и затем расшифровывается правильным ключом.
- **Then** столбцы `request`/`response` содержат AEAD-шифротекст (nonce+tag+ct), не содержат plaintext-фрагментов prompt'а; расшифровка рабочим ключом восстанавливает содержимое, любым другим ключом — ошибка аутентификации.
- Evidence: `pg_dump`/select показывает бинарный ciphertext без читаемого контента; unit-тест «decrypt wrong key → error».

### AC-005 Detail API отдаёт base64-обёртку

- Почему это важно: предписанный формат передачи на фронт.
- **Given** admin-сессия и существующая запись.
- **When** `GET /api/v1/conversations/:id`.
- **Then** ответ содержит метаданные и `payload` с полями `request`, `response` и `masking`, каждое — base64 расшифрованного содержимого; `atob(payload.request)` возвращает исходный prompt; `atob(payload.masking)` + JSON.parse — массив пар «плейсхолдер → оригинал» (или null, если mask не применялся).
- Evidence: curl ответа + декодирование `base64 -d` (или `atob` в браузере) даёт исходные строки и mask-доказательства; unit/integration-тест на DTO.

### AC-006 List API — только метаданные

- Почему это важно: список не должен светить содержимым и должен уметь фильтровать.
- **Given** записи в БД; admin-сессия.
- **When** `GET /api/v1/conversations` (с опциональными `page`, `per_page`, `tenant_id`).
- **Then** возвращается пагинированный список из `id`, `tenant_id`, `model`, `status`, `masked`, `streamed`, `created_at` — без содержимого и без `payload` (mask-доказательства тоже не выводятся в списке).
- Evidence: curl показывает список метаданных; в ответе нет ключей `request`/`response`/`masking`/`payload`.

### AC-007 TTL cleanup

- Почему это важно: предотвращает неограниченный рост зашифрованных данных.
- **Given** запись старше `CONFIG`-TTL и включённый cleanup worker.
- **When** cleanup-цикл отрабатывает.
- **Then** запись удаляется; свежие записи остаются.
- Evidence: unit-тест cleanup worker с записями разного возраста (по образцу `cleanup_worker_test.go`).

### AC-008 Fail-closed при отсутствии ключа

- Почему это важно: исключить случайное plaintext-хранение при misconfig.
- **Given** фича включена в конфиге.
- **When** запуск gateway/admin: (а) без ENV-ключа; (б) с корректным ключом.
- **Then** (а) процесс завершается с понятной ошибкой и ненулевым exit code; (б) стартует нормально.
- Evidence: ручной запуск `make build && ./bin/gateway` без ключа — non-zero exit + сообщение; unit-тест конструктора крипто-пакета.

### AC-009 Страница Conversations в UI

- Почему это важно: пользовательская цель фичи.
- **Given** admin залогинен; существуют записи.
- **When** переход на `/conversations`.
- **Then** страница показывает список (tenant, model, время, статус); у записи — деталь с request/response, полученными из `payload` и декодированными `atob`; при отсутствии данных — пустое состояние.
- Evidence: ручной UI-чек; корректное рендерение request/response из base64; компонент-тест декодирования.

### AC-010 Data plane устойчив к сбоям захвата

- Почему это важно: логирование не должно ломать прокси (RQ-006) — иначе сбои конвейера превращаются в отказы трафика.
- **Given** включённая фича; шифрование или запись в БД во время обработки запроса падает (encryptor/store error).
- **When** non-streaming запрос обрабатывается сквозь proxy chain (для streaming — middleware-компонент capture также не прерывает поток).
- **Then** клиент получает штатный ответ (статус и тело как без лог-конвейера); запись для этого запроса не сохранена; ошибка захвата/шифрования/сохранения залогирована (warn) с `trace_id`; обработка не прерывается.
- Evidence: integration-тест middleware с фейковым encryptor/store, возвращающим ошибку → response 200 доходит до клиента, обработка продолжилась, `Save` вернул ошибку без паники; никаких 5xx из-за лог-конвейера.

### AC-011 Асинхронная запись не влияет на ответ клиента

- Почему это важно: шифрование и БД-операции уходят с горячего пути (RQ-008) — latency data plane не зависит от конвейера логов.
- **Given** включённая фича; non-streaming запрос; worker с искусственно замедленной/блокирующей записью в БД.
- **When** запрос обрабатывается.
- **Then** ответ клиенту завершается до завершения записи в БД (клиент не ждёт worker); на горячем пути выполняется только буферизация тела + enqueue в канал воркера, без крипты и DB-вызовов; запись позже доезжает в БД.
- Evidence: integration/unit-тест: mock-канал/воркер с задержкой → handler отвечает немедленно (замер времени/порядок); инспекция кода middleware подтверждает отсутствие crypto/DB на hot path.

## Допущения

- Ключ шифрования: 32 случайных байта, base64-строка, ENV-переменная `MASKCHAIN_CONVERSATION_KEY` (читается напрямую `os.Getenv`, не через `CONFIG_*`/config.yaml); одна и та же у gateway и admin.
- Схема: случайный 12-байтовый nonce на запись, хранится вместе с ciphertext.
- «Запрос» = оригинальный `messages`-массив из тела как получен gateway (до mask-преобразования shield), включая все роли; «ответ» = финальное тело ответа как отдано клиенту (после unmask): для non-streaming — JSON-тело, для streaming — verbatim SSE-лента (`data: ...\n\n` + `[DONE]`). То, что буквально ушло провайдеру (с плейсхолдерами mask), отдельно НЕ хранится: вместо дублирования контента хранится доказательство mask — mapping «плейсхолдер → оригинал» (merged dict+PII от shield) как `masking`-поле, а булев `masked` = `masking != null`. Так администратор видит, что именно и как было замаскировано (ядро ценности фичи).
- Mask-доказательство: многокартовый массив `[{"placeholder": "[MASK_abc.3]", "original": "..."}]`; маппинг строится shield-мидлварой и передаётся conversation-логгеру через gin context (см. Контекст).
- Асинхронность: на горячем пути (в middleware) — только чтение тела, буферизация ответа и enqueue «сырых» данных в канал; worker в фоновой goroutine шифрует все поля (request/response/masking) и батчами пишет в БД (RQ-008). Резерв: данные, не успевшие вылететь при падении процесса, теряются — приемлемо для логов.
- Стриминг: для `stream: true` ответ захватывается как verbatim SSE-лента (все `data: ...`-части и терминатор `[DONE]`), как отдана клиенту после unmask по чанкам; обрезка до 1 МБ применяется к накопленной ленте; флаг `streamed=true` отличает такие записи от non-streaming JSON-ответов.
- Захват не зависит от наличия `X-Session-ID`.
- Ограничение размера: содержимое запроса/ответа обрезается до 1 МБ перед шифрованием/записью (обрезка с начала строки), чтобы не раздувать БД.
- Запись для запроса без контента (`messages` пустые или без содержимого) не создаётся — исключаем шумные строки в логе разговоров.
- Механизм шифрования: AEAD-симметричное шифрование с секретным ключом; случайный nonce на запись хранится вместе с ciphertext. Конкретный крипто-механизм и формат записи закреплены в plan (DEC-003/DEC-004); в spec фиксируется только свойство at-rest из RQ-002.

## Критерии успеха

- SC-001: overhead на data plane для запроса — только буферизация + enqueue (для streaming — поблочный проход через буфер без задержки чанков); crypto и DB полностью на фоне (median дополнительной задержки ответа < 0.2 мс на типовых размерах).
- SC-002: при выходе из строя шифрования/записи — error rate прокси не растёт (среднее отклонение < 0.1% на тестовом прогоне).

## Краевые случаи

- Пустое содержимое: `messages` без контента → запись не создаётся (шумные строки исключены); поведение зафиксировано в Допущениях.
- Ответ без тела/ошибка upstream (5xx) — записывается с фактическим `status`, `response` по факту.
- Streaming с обрывом соединения/без `[DONE]` — записывается с `streamed=true` и `status=error`, response = то, что успело уйти клиенту (до 1 МБ).
- Streaming, заблокированный shield (403) — запись со `streamed=true`, `status=blocked`, response по факту (как и для non-streaming blocked).
- Дубликат/повторная отправка одного запроса — каждая запись уникальна по UUID, идемпотентность не требуется.
- Запись при выключенной фиче — не создаётся ничего.
- Первая строка списка при отсутствии данных — пустое состояние UI.
- Admin пытается открыть несуществующий id — 404.
